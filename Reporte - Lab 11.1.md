# **Lab 11.1 – Orquestando funciones serverless con AWS Step Functions para la generación de reportes**

En este laboratorio implementé un flujo de trabajo serverless completo utilizando AWS Step Functions para coordinar varias funciones de AWS Lambda, Amazon SNS, Amazon S3, Amazon RDS y API Gateway. El objetivo general fue lograr que Frank, el dueño de la cafetería, pudiera solicitar un reporte actualizado del inventario de granos de café a través de una API REST y recibir por correo electrónico un enlace (URL prefirmada) para descargar dicho reporte desde un bucket de S3. Todo el flujo se diseñó de forma desacoplada, automatizada y segura, utilizando una máquina de estado que orquesta la consulta de datos, la generación del HTML y el envío de la URL.

- ### **Tarea 1: Preparación del entorno de desarrollo**
En la primera tarea me enfoqué en dejar listo el entorno técnico sobre el que iba a trabajar. Primero confirmé en la consola de CloudFormation que la pila asociada al laboratorio estuviera en estado CREATE_COMPLETE, ya que esa plantilla es la encargada de crear recursos base como el bucket de S3, la base de datos Aurora Serverless (MySQL), la API REST previa, la tabla DynamoDB, el clúster de caché y el entorno de Elastic Beanstalk, entre otros. Sin esa pila funcionando correctamente, el laboratorio no podría continuar.
Después accedí al IDE de VS Code en el navegador usando la URL y contraseña proporcionadas por el laboratorio. Una vez dentro, descargué el archivo code.zip con los recursos específicos de este lab y lo descomprimí. A continuación ejecuté el script setup.sh, dándole mi dirección IPv4 pública para que ajustara las políticas del bucket de S3 y de otros recursos, restringiendo el acceso al rango correcto. Verifiqué también que la versión de la AWS CLI instalada fuera la 2, y que el SDK de Python (boto3) estuviera disponible. Finalmente comprobé que el sitio web de la cafetería se pudiera cargar desde el bucket de S3, lo que confirmó que la infraestructura básica estaba en orden y que podía continuar con las partes lógicas del flujo de reportes.

- ### **Tarea 2: Configuración del tema de SNS y suscripción por correo**
En la segunda tarea preparé el mecanismo de notificación que Frank utilizará para recibir el enlace del reporte. Para ello creé un tema de Amazon SNS llamado EmailReport de tipo estándar. Lo configuré con una política de acceso abierta a “todos” tanto para publicar como para suscribirse, ya que en el contexto del laboratorio se simplifica la parte de seguridad para enfocarse en la orquestación.
Después añadí una suscripción de tipo correo electrónico a ese tema, usando una dirección en la que pudiera recibir los mensajes. Desde el correo de confirmación de AWS Notifications validé la suscripción haciendo clic en el enlace correspondiente. Para asegurarme de que todo funcionaba correctamente, publiqué un mensaje de prueba en el tema EmailReport directamente desde la consola de SNS, con un asunto y cuerpo simples. Pocos momentos después recibí el correo, lo que confirmó que el canal de notificación ya estaba listo para integrarse con Step Functions más adelante.

- ### **Tarea 3: Creación de la máquina de estado básica en Step Functions**
En la tercera tarea comencé a trabajar con AWS Step Functions. Primero revisé el rol de IAM RoleForStepToCreateAReport, que ya venía preconfigurado para el laboratorio. Analicé sus políticas adjuntas y confirmé que permitían a Step Functions invocar funciones Lambda y escribir logs, así como que la relación de confianza autorizaba al servicio states.amazonaws.com a asumir dicho rol.
Con esto claro, pasé a la consola de Step Functions y creé una máquina de estado nueva llamada MyStateMachine usando un lienzo en blanco. En el Workflow Studio arrastré un estado de tipo Amazon SNS Publish y lo configuré para que publicara en el tema EmailReport que había creado en la tarea anterior. La máquina de estado estaba diseñada para tomar la entrada de ejecución y utilizarla como mensaje del correo. Luego asocié la máquina al rol RoleForStepToCreateAReport y habilité el nivel de logging en ALL.
Para probarla, ejecuté la máquina con un input JSON sencillo donde incluía una cadena en el campo presigned_url_str que decía “Testing that my email message works”. Al iniciar la ejecución, Step Functions invocó SNS y poco después recibí un correo con ese texto en el cuerpo del mensaje. Esta prueba validó que la máquina de estado era capaz de integrarse con SNS y enviar notificaciones de forma automática.

- ### **Tarea 4: Generación de una URL prefirmada con Lambda y S3**
En la cuarta tarea enfoqué el trabajo en el manejo de archivos en S3 y en la generación de URLs prefirmadas. Primero, desde el IDE, creé un archivo HTML sencillo llamado report.html con contenido de prueba (“Hello! This is some sample HTML.”) y lo subí al bucket de S3 asociado al sitio de la cafetería usando la AWS CLI. Después revisé la política del bucket, donde se especificaba que la acción s3:GetObject sería denegada para report.html a menos que la solicitud usara autenticación basada en cadena de consulta (REST-QUERY-STRING), lo que se alinea con el uso de URLs prefirmadas.
Luego intenté acceder directamente al objeto mediante su URL pública y, como se esperaba, recibí un error AccessDenied. Para comprobar la lógica de seguridad, generé desde la CLI una URL prefirmada con aws s3 presign, configurando una expiración de 30 segundos. Dentro de ese periodo, al abrir la URL se cargó correctamente el HTML de prueba; pasado el tiempo de expiración, la misma URL dejó de ser válida y volvió a mostrar AccessDenied. Esto me permitió entender claramente cómo la política del bucket y las URLs prefirmadas trabajan juntas para controlar el acceso.
Con esa base, creé una función Lambda llamada GeneratePresignedURL en Python 3.9, utilizando el rol RoleForAllLambdas. En el código inicialicé un cliente de S3 y dentro del handler generé una URL prefirmada apuntando al archivo report.html del bucket de la cafetería, con una expiración mayor (por ejemplo, 120 segundos). Después probé la función desde la consola de Lambda, obteniendo la URL prefirmada en la respuesta y verificando que al abrirla podía ver el reporte de ejemplo. Esta función sería el componente encargado de producir la URL que más adelante será enviada por correo.
Finalmente, volví a Step Functions y actualicé la máquina de estado MyStateMachine para invocar primero la función Lambda GeneratePresignedURL y, a continuación, usar el estado SNS Publish para enviar por correo la URL devuelta. Probé de nuevo la máquina, esta vez sin pasar payload en la entrada, y revisé el correo con la URL prefirmada, confirmando que podría encadenar Lambda y SNS dentro del flujo.

- ### **Tarea 5: Integración de API Gateway con Step Functions**
En la quinta tarea conecté la parte de orquestación con una API REST para que el flujo se pudiera disparar externamente, tal como lo haría Frank desde el sitio web. Empecé revisando el rol de IAM RoleForAPIGWToTriggerStep, que permite a API Gateway invocar Step Functions y escribir logs, y también comprobé su relación de confianza con el servicio apigateway.amazonaws.com.
Luego entré a la consola de API Gateway y localicé la API ProductsApi, que ya existía de laboratorios anteriores. Dentro del recurso /create_report en el método POST, edité la Solicitud de integración para que en lugar de invocar Lambda, ahora llamara a Step Functions usando el método StartExecution. Configuré el tipo de integración como “Servicio de AWS”, seleccioné Step Functions en la región us-east-1, indiqué el rol RoleForAPIGWToTriggerStep y definí una plantilla de mapeo application/json que construye el cuerpo de la petición con dos campos: input, que es el JSON de entrada escapado, y stateMachineArn, que apunta al ARN de MyStateMachine.
Después de guardar los cambios, probé el método POST directamente desde API Gateway. La respuesta fue un JSON con el executionArn y un startDate, lo que significa que API Gateway estaba iniciando correctamente la ejecución de la máquina de estado. Más tarde desplegué la API en el stage prod y obtuve la URL de invocación. Desde el terminal del IDE ejecuté un curl -X POST hacia invoke-url/create_report y, nuevamente, el sistema respondió con los datos de la ejecución. Al revisar el correo, encontré el mensaje con la URL prefirmada, confirmando que ahora Frank podría disparar todo el flujo simplemente llamando al endpoint REST, sin tener que entrar a la consola de AWS.

- ### **Tarea 6: Creación de la función Lambda para generar el HTML del reporte**
En la sexta tarea pasé de un HTML de ejemplo a un reporte dinámico. Para ello creé una nueva función Lambda llamada generateHTML con runtime Node.js 20.x, usando de nuevo el rol RoleForAllLambdas. Aumenté el timeout a 2 minutos para tener margen en la generación del archivo.
En el código de la función implementé la lógica para: recibir un objeto JSON con la estructura my_json_arr, construir una página HTML con estilos CSS integrados y subir el resultado al bucket S3 de la cafetería bajo el nombre report.html. El HTML incluye un encabezado de reporte, un timestamp y secciones por proveedor, donde muestro el nombre, la dirección y los diferentes tipos de granos disponibles, junto con sus cantidades y nombres de producto. La función utiliza el cliente de S3 de la AWS SDK v3 para hacer un PutObject con el contenido HTML y configura CacheControl y ContentType apropiadamente. Además, también genera de nuevo una URL prefirmada del mismo archivo para devolverla en la respuesta, aunque en la lógica final quien se encarga de enviar la URL por correo es otra función Lambda acoplada a la máquina de estado.
Para probarla, definí un evento de prueba en Lambda con un JSON de ejemplo que incluía dos proveedores y varios tipos de grano. Al ejecutar la función recibí un mensaje indicando que el reporte había sido publicado en S3. Aunque por políticas del bucket no podía abrir el archivo directamente desde la consola, podría verlo posteriormente a través de una URL prefirmada. Con esto, la función generateHTML quedó lista para integrarse en el flujo general.

- ### **Tarea 7: Ejecución en paralelo de la generación de HTML y la URL prefirmada**
En la séptima tarea regresé a Step Functions para optimizar el flujo utilizando estados paralelos. La idea fue que la generación del HTML del reporte y la generación de la URL prefirmada se ejecutaran al mismo tiempo, ya que no dependen secuencialmente una de la otra en esta versión del laboratorio. De esta forma, el tiempo total de ejecución puede reducirse.
En el diseñador de la máquina de estado agregué un estado de tipo Parallel llamado Process Report encima de los estados de Lambda que ya tenía. Dentro de ese estado paralelo coloqué dos ramas: en una rama la invocación a la función generateHTML y en la otra la función GeneratePresignedURL. Configuré la rama de generateHTML para que utilizara como payload la entrada del estado (que contiene my_json_arr) y que al terminar marcara el final de esa rama. La otra rama generaba la URL prefirmada para report.html. Una vez que ambas ramas finalizan, el estado paralelo continúa y pasa al estado SNS Publish, que se encarga de enviar por correo el resultado.
> Probé este diseño ejecutando la máquina de estado con un JSON de entrada que contenía un arreglo de proveedores, similar al usado en las pruebas anteriores. Tras la ejecución, recibí un correo con un cuerpo en formato JSON que incluía tanto el mensaje “Report published to S3” como la presigned_url_str. Abrí la URL y pude ver el reporte HTML formateado con los proveedores y granos definidos. Esto demostró que los estados paralelos estaban funcionando correctamente y que el flujo se había vuelto más eficiente.

- ### **Tarea 8: Creación de la función Lambda para obtener datos reales desde RDS**
En la octava tarea dejé de usar datos de prueba y empecé a trabajar con los datos reales almacenados en la base de datos MySQL de Amazon Aurora Serverless. Creé una nueva función Lambda llamada generateReportData con Node.js 20.x y el rol RoleForAllLambdas. Esta función es la encargada de conectarse a la base de datos, ejecutar consultas y transformar los resultados en el formato JSON que el resto del flujo espera.
Para ello, desde el IDE de VS Code creé un directorio lambda con un archivo index.js y un package.json. En el package.json declaré las dependencias mysql2 y @aws-sdk/client-s3, y luego ejecuté npm install y generé un archivo lambda.zip con el código y los módulos. En index.js implementé la lógica para conectarme al endpoint de la base de datos (que obtuve desde la consola de RDS), autenticarme con el usuario nodeapp y el password coffee, y ejecutar dos consultas: una sobre la tabla de proveedores y otra sobre la tabla de beans. Después fusioné la información en una estructura de arreglo donde cada proveedor contiene un arreglo anidado con los tipos de grano, su nombre de producto y su cantidad. Todo esto se devuelve como my_json_arr dentro del cuerpo de la respuesta.

> Subí el archivo lambda.zip a la función generateReportData en la consola de Lambda y configuré la función para que se ejecutara dentro de la VPC del laboratorio, seleccionando las subredes y el grupo de seguridad que permiten la conexión a la base de datos. Tras esperar a que se propagara la actualización de VPC, probé la función con un evento de prueba vacío. La respuesta incluyó los registros reales de la base de datos de proveedores y sus granos, confirmando que la función podía consumir los datos de RDS desde una subred privada de forma exitosa.

- ### **Tarea 9: Integración final de generateReportData en la máquina de estado y prueba end-to-end**
En la última tarea integré todos los componentes dentro de la máquina de estado de Step Functions para completar el flujo end-to-end. En el diseñador agregué un nuevo estado de tipo AWS Lambda Invoke llamado getRealData, ubicado antes del estado paralelo Process Report. Configuré este estado para invocar la función generateReportData sin payload de entrada. El resultado de esta función, que contiene my_json_arr con los datos reales, se convierte en la entrada que posteriormente utilizan tanto generateHTML como GeneratePresignedURL dentro del estado paralelo.
Probé la máquina de estado ejecutándola desde la consola de Step Functions con un input vacío {}. Durante la ejecución, primero se llamó a getRealData, que consultó la base de datos de Aurora, luego el estado Process Report generó el HTML actualizado y la URL prefirmada en paralelo, y finalmente SNS envió el correo. Al revisar mi bandeja de entrada, encontré un correo con la estructura esperada, copié la URL prefirmada en el navegador y se cargó un informe HTML con la información real de los proveedores y sus inventarios. Cuando dejé pasar más tiempo y volví a refrescar la página, la URL había caducado, demostrando que el acceso al reporte está temporalmente limitado.

> Para cerrar el ciclo completo, volví a API Gateway, tomé la URL de invocación del stage prod y ejecuté un curl -X POST https://.../prod/create_report. La respuesta mostró el executionArn de Step Functions y, unos momentos después, nuevamente recibí el correo con el enlace al reporte actualizado. Esto confirmó que la integración entre API Gateway, Step Functions, Lambda, RDS, S3 y SNS estaba funcionando de punta a punta, tal como se planteó en el escenario del laboratorio.

- ### **Conclusión general**
En resumen, en este laboratorio diseñé e implementé un flujo de orquestación serverless completo usando AWS Step Functions como componente central. A partir de un simple endpoint REST, el sistema consulta datos reales en una base de datos MySQL en Amazon RDS, genera un reporte HTML en un bucket de S3, crea una URL prefirmada de acceso temporal y envía esa URL por correo electrónico a través de Amazon SNS. A lo largo de las tareas trabajé con varios servicios de AWS (Lambda, S3, RDS, API Gateway, SNS, IAM y VPC), reforzando conceptos como integración de servicios, seguridad con políticas y roles, URLs prefirmadas, ejecución paralela y desacoplamiento de componentes. Desde la perspectiva de la cafetería, Frank ahora puede solicitar reportes bajo demanda sin conocer los detalles técnicos del backend, mientras que el sistema garantiza que siempre reciba información actualizada y accesible solo durante un tiempo limitado.
