- ### **Tarea 2**
En la segunda parte configuré la distribución de CloudFront para el contenido estático del sitio. Desde la consola de CloudFront creé una nueva distribución, usando como origen el bucket de S3 del sitio. Para controlar el acceso al bucket activé una Origin Access Identity heredada (OAI), le puse el nombre access-identity-cafe-website y permití que CloudFront actualizara la política del bucket para que solo la distribución pudiera leer los objetos. Además, agregué un encabezado personalizado cf=1 que se usará en un laboratorio posterior. En el comportamiento de caché predeterminado mantuve el patrón de ruta por defecto (*) y configuré la política de protocolo del visor en “Redirect HTTP to HTTPS” para que cualquier intento por HTTP se redirigiera automáticamente a HTTPS. Dejé los métodos permitidos en GET y HEAD, y no restringí el acceso del visor para que fuera un sitio público. En la sección de caché elegí usar la configuración heredada y “Use origin cache headers”, de manera que la distribución respetara los encabezados Cache-Control que ya tenían los objetos en S3. Como no se trabajó con dominios personalizados, usé el certificado por defecto de CloudFront (*.cloudfront.net), seleccioné HTTP/2 como versión soportada, desactivé IPv6 y configuré index.html como el objeto raíz predeterminado. Después de crear la distribución, esperé a que cambiara el estado a Enabled y tomé nota del dominio generado que termina en .cloudfront.net.

Una vez que la distribución estuvo implementada, actualicé la política del bucket de S3 para bloquear el acceso directo. En la pestaña de permisos eliminé las líneas de la política que permitían s3:GetObject desde mi dirección IP. Al refrescar la URL directa del objeto index.html, el navegador mostró un error AccessDenied, lo cual era justo lo esperado, porque ahora el bucket ya no debía servir el sitio directamente al público. Desde ese momento la única forma correcta de acceder al sitio de la cafetería fue mediante la URL de CloudFront. Probé la URL de la distribución en el navegador y verifiqué que el sitio se cargara ahora mediante HTTPS. También, como plantea el laboratorio, la idea era probar el acceso desde otra red (por ejemplo, desde un móvil con datos celulares o usando wget desde el IDE), para confirmar que la distribución funcionaba desde distintas ubicaciones físicas, demostrando el alcance global de CloudFront.

- ### **Tarea 3**
La siguiente parte del laboratorio se centraba en la seguridad de red con AWS WAF para la distribución de CloudFront. A nivel conceptual, la idea es que antes la restricción de acceso desde una IP específica se hacía en la política del bucket de S3, pero ahora, al mover el frontend detrás de CloudFront, esa lógica de “solo desde la oficina” tenía que trasladarse a la capa del CDN. Para lograr esto, se crea primero un conjunto de IP (IP set) global en WAF & Shield, por ejemplo office, donde se registra la dirección IPv4 pública de la oficina en formato <ip>/32. Luego se crea una Web ACL global llamada algo como cafe-website-office-only-during-dev, se asocia a la distribución de CloudFront y se añade una regla del tipo IP set (only_office_please) con acción Allow para el conjunto office. Finalmente, la acción predeterminada de la ACL se configura en Block, de modo que todo lo que no venga de esa IP quede bloqueado. En la consola de CloudFront, la distribución aparece ahora vinculada a una ACL de WAF, y al probar el sitio se comprueba que desde la IP registrada la página se carga con normalidad, mientras que desde otras redes devuelve errores de acceso (403), lo que demuestra que el control ahora lo ejerce AWS WAF.

- ### **Tarea 4**
En la tarea 4 el laboratorio aplica el mismo enfoque, pero sobre un endpoint específico de la API de REST en API Gateway, en este caso el recurso /bean_products que se invoca desde el sitio vía AJAX. Aquí el objetivo es que no cualquiera en internet pueda llamar directamente a la URL de la API, sino únicamente la IP de la “oficina”. Para ello se crea un IP set regional (por ejemplo office_regional) en la región US East (N. Virginia) con la misma dirección IP/32, luego una Web ACL regional llamada website-api-gw-office-only-during-dev, asociada al recurso ProductsApi - prod de API Gateway. Se añade una regla ip_for_apigw basada en el IP set regional con acción Allow, y nuevamente la acción por defecto de la ACL se pone en Block. Al probar la URL de invocación desde el navegador del equipo (o con wget), la respuesta correcta es un JSON con los productos, mientras que desde otra red (o desde el IDE) la respuesta esperada es {"message": "Forbidden"} o un código HTTP 403, confirmando que también la API quedó protegida por WAF.
- ### **Tarea 5**

Más adelante, el laboratorio describe el uso de CloudFront Functions para personalizar dinámicamente la imagen del postre destacado en la página de inicio sin tener que cargar toda la lógica en el navegador. La idea es crear una función de CloudFront llamada random_image_header, pegar un pequeño código en JavaScript que construye una cookie llamada the_image con un valor aleatorio tomado de un arreglo de nombres de postres (por ejemplo apple_pie, chocolate_chip_cupcake, etc.) y ajustar el dominio de la cookie al dominio de la distribución. Esta función se prueba con un evento de tipo Viewer Response y luego se publica y se asocia a la distribución de CloudFront en el evento Viewer Response del comportamiento por defecto. Cada vez que CloudFront responde, la función añade la cookie con el nombre del postre y, gracias al código JavaScript ya incluido en el sitio (en scripts.main.js), la página cambia la imagen que aparece a la derecha de la taza de café, de manera que en cada actualización del navegador puede mostrarse un postre distinto.
- ### **Tarea 6**
Finalmente, la tarea 6 se enfoca en el tema del almacenamiento en caché. Al inicio del laboratorio todos los archivos del bucket tenían Cache-Control: max-age=0, lo que facilita ver cambios inmediatos durante el desarrollo pero no aprovecha el potencial de un CDN. Para ajustar esto, se ejecuta en el terminal un comando de AWS CLI que recorre todos los objetos del bucket y los reescribe con un nuevo encabezado Cache-Control: max-age=180, es decir, 180 segundos (3 minutos). Después se verifica en la consola de S3 que los metadatos de los objetos tengan ese valor. Desde el navegador, con las herramientas de desarrollador, se observa que el encabezado cache-control ahora muestra max-age=180 y que el encabezado x-cache empieza a mostrar “Hit from cloudfront” cuando las respuestas se sirven desde caché, y “RefreshHit from cloudfront” después de que expira el tiempo de vida y CloudFront tiene que actualizar el contenido desde el origen. Lo interesante es que, incluso con la caché activa, la imagen del postre sigue cambiando gracias a la cookie que maneja CloudFront Functions, lo cual demuestra cómo se pueden combinar caché y personalización desde la periferia.
