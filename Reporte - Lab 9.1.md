# **Reporte – Lab 9.1: Caching Application Data with ElastiCache**

En este laboratorio trabajé en mejorar el rendimiento de la aplicación de proveedores de café utilizando Amazon ElastiCache para Memcached como una capa de caché entre la aplicación y la base de datos Aurora Serverless. La idea central era abordar un problema real que experimentaba la cafetería: los clientes reportaban que la página tardaba demasiado en mostrar el inventario de granos, lo cual se debía a que la aplicación siempre consultaba la base de datos directamente. Implementar una caché permitiría agilizar estas consultas, especialmente para datos que no cambian con mucha frecuencia.

Para comenzar, preparé el entorno de desarrollo usando el IDE basado en VS Code que el laboratorio proporciona. Después de conectarme, descargué los archivos necesarios y ejecuté el script setup.sh, que reconstruyó toda la arquitectura backend que ya se había trabajado en laboratorios anteriores: la aplicación de proveedores de café en Elastic Beanstalk, la base de datos Aurora Serverless, la API de REST y los buckets de S3 usados por el sitio web. Verifiqué también que la CLI de AWS y las dependencias de Python estuvieran correctamente instaladas, ya que más adelante utilizaría scripts de prueba escritos en Python para interactuar con la caché y con Aurora.

Una parte clave del laboratorio fue la configuración de la red, ya que tanto Memcached como Aurora debían poder comunicarse entre sí y con el IDE. Para ello, edité el grupo de seguridad asociado a Aurora, permitiendo tráfico TCP en el puerto 11211 (puerto estándar de Memcached) tanto desde ese mismo grupo como desde el grupo de seguridad del IDE. Posteriormente, configuré un grupo de subredes para ElastiCache, el cual define en qué subredes privadas se implementarían los nodos del clúster. Con esto, la base estaba lista para desplegar Memcached.

La siguiente etapa consistió en crear el clúster de ElastiCache, seleccionando Memcached versión 1.6.6, con un total de tres nodos cache.r6g.large. Este clúster tardó unos minutos en pasar al estado “available”, pero una vez listo pude obtener su endpoint para usarlo en los scripts. Del mismo modo, recuperé el endpoint de Aurora usando comandos de AWS CLI. Ambos endpoints serían importantes para conectar los scripts de Python con los servicios.

Las pruebas comenzaron con el script find_all.py, el cual implementaba una estrategia de carga diferida (lazy loading). En este patrón, los datos solo se guardan en caché si no existen allí; es decir, el script primero intentaba leer la clave all_beans desde Memcached, y si no estaba disponible, hacía un SELECT * FROM beans directamente en Aurora, convertía el resultado a JSON y lo guardaba en la caché con un TTL de 180 segundos. Al ejecutar este script por primera vez, efectivamente los datos salieron desde la base de datos y se almacenaron en la caché. En la segunda ejecución, antes de que el TTL expirara, los resultados se devolvieron directamente desde la caché, lo cual redujo considerablemente el tiempo de respuesta.

Después probé las operaciones de escritura, comenzando con el script update_item.py. Este script hacía un UPDATE sobre un registro en Aurora y luego invalidaba la caché, eliminando la clave all_beans. Esto es parte de la estrategia de write-through con invalidación, que asegura que la caché nunca muestre información desactualizada. Al ejecutar nuevamente find_all.py, los datos se refrescaron correctamente y se volvieron a almacenar en Memcached con el registro actualizado.

El laboratorio continuó con las operaciones de creación (create_item.py) y eliminación (delete_item.py). En ambos casos se seguía el mismo patrón: al insertar o eliminar un registro de la base de datos, se purgaba la caché para evitar inconsistencias. Cada una de estas pruebas confirmó que el mecanismo de sincronización entre Aurora y Memcached funcionaba como se esperaba, asegurando que la aplicación pudiera confiar en la caché sin riesgo de mostrar información incorrecta.

En la parte final del laboratorio trabajé en la actualización de la aplicación de proveedores de café. El archivo bean.controller_2.js contenía una nueva versión del controlador que conocía la existencia de la caché. El código incluía la variable de entorno MEMC_HOST, que serviría para indicar el endpoint de Memcached, y también implementaba una optimización adicional: en lugar de almacenar únicamente todos los granos bajo la clave all_beans, también almacenaba elementos individuales con claves del tipo beans_<id>. Esto permitiría recuperar datos específicos sin depender exclusivamente de la lista completa.

Luego de reemplazar el controlador antiguo por el nuevo, reconstruí la imagen Docker de la aplicación, instalé sus dependencias y envié la imagen actualizada a su repositorio en Amazon ECR. Una vez hecho esto, la aplicación en Elastic Beanstalk pudo actualizarse automáticamente. El último paso fue añadir la variable de entorno MEMC_HOST con el endpoint del clúster de ElastiCache dentro de la configuración del entorno, lo que permitió que la aplicación comenzara a utilizar la caché correctamente. Al abrir la aplicación y navegar hacia /beans, pude ver una nota indicando si los datos estaban viniendo desde la base de datos o desde la caché, confirmando que la integración estaba funcionando.

Finalmente, verifiqué la experiencia desde el sitio web de la cafetería. Desde la sección Buy Coffee, la lista de granos coincidía exactamente con la que se había probado en los scripts y en la aplicación, lo cual demostraba que todos los componentes —ElastiCache, Aurora y Elastic Beanstalk— estaban trabajando coordinadamente.
- ### **Conclusión**
En conclusión, este laboratorio me permitió implementar una solución de cacheo real utilizando ElastiCache para reducir la latencia del sitio web de la cafetería y aliviar la carga sobre la base de datos. A través de varias pruebas de lectura y escritura, comprobé cómo mantener la coherencia entre la base de datos y la caché aplicando estrategias como carga diferida e invalidación. Además, integré la caché en una aplicación Node.js usando prácticas recomendadas como variables de entorno y almacenamiento de claves granular. El resultado final fue una aplicación significativamente más rápida y eficiente, capaz de ofrecer una mejor experiencia a los usuarios sin sacrificar consistencia ni confiabilidad.
