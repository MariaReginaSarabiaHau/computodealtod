# **Lab 13.1 – Automatizando despliegues con una canalización CI/CD (CodeCommit + CodePipeline)**
En este laboratorio trabajé de nuevo desde el papel de Sofía, pero ahora con un enfoque totalmente orientado a la automatización. El sitio web de la cafetería ya está en producción, así que Frank pidió dos cosas muy claras: centralizar el código con control de versiones y dejar de depender de cargas manuales al bucket de S3 cada vez que se haga un cambio. El objetivo fue construir un flujo de integración y entrega continua (CI/CD) utilizando AWS CodeCommit como repositorio Git privado y AWS CodePipeline como canalización que detecta cambios y actualiza automáticamente el sitio web estático hospedado en Amazon S3 y entregado por CloudFront. Al final del laboratorio, la idea es que cualquier cambio confirmado en el repo se convierta en una actualización automática del sitio de la cafetería.

- ### **Tarea 1: Preparar el entorno de desarrollo**
La primera parte del laboratorio consistió en dejar el entorno de desarrollo listo para poder trabajar con la canalización. Igual que en labs anteriores, abrí el IDE de VS Code a través de la URL proporcionada en la consola de laboratorio y me autenticqué usando la contraseña temporal. Antes de tocar nada, revisé en AWS CloudFormation que las tres pilas asociadas al laboratorio estuvieran en estado CREATE_COMPLETE, porque a través de esas plantillas se recrea toda la arquitectura previa: bucket de S3 del sitio, API Gateway, DynamoDB, aplicación de proveedores en Elastic Beanstalk, etc.
Dentro del terminal de VS Code descargué el archivo code.zip específico de este laboratorio y lo descomprimí en el directorio environment. Después ejecuté el script setup.sh, que no solo actualiza la versión de la AWS CLI a la serie 2, sino que también reconstruye los recursos clave de los labs anteriores (bucket del sitio de la cafetería, tabla de DynamoDB con datos de menú, API REST, etc.). El script me pidió dos datos importantes: mi dirección IPv4 pública (para restringir acceso al bucket vía política de S3) y un correo electrónico válido (para futuras notificaciones). Al terminar, verifiqué con aws --version que la CLI 2 estuviera instalada y comprobé que el SDK de Python boto3 estuviera disponible. Con esto, el entorno de desarrollo quedó listo para crear el repositorio y la canalización.

- ### **Tarea 2: Crear el repositorio de CodeCommit**
Con el entorno listo, el siguiente paso fue resolver el problema del control de versiones. Hasta ahora el código del sitio vivía prácticamente “suelo” en archivos locales y en el bucket de S3, sin un sistema formal de cambios. Para resolver esto, fui a la consola de AWS CodeCommit y creé un repositorio nuevo llamado front_end_website, con una descripción que dejara claro que es el repositorio del front del sitio de la cafetería.
Como parte del laboratorio, no solo se creó el repo vacío, sino que agregué un primer archivo de prueba directamente desde la consola de CodeCommit. Usé la opción “Create file” y pegué un pequeño HTML muy sencillo (test.html) con un título y un encabezado. En la sección de commit ingresé mi nombre, mi correo y el mensaje “This is my first commit.” para registrar este primer cambio en la rama main. Una vez hecho el commit, revisé la sección de “Commits” del repositorio para asegurarme de que el archivo estaba ahí y que los metadatos (autor, mensaje, fecha) se habían guardado correctamente.
Como detalle adicional, agregué un comentario en línea sobre el archivo test.html, usando el ícono de comentario a un lado del número de línea. Escribí algo como “I must add a better title at some point.”, simulando una nota futura de mejora. Esto muestra cómo CodeCommit también se puede usar para revisiones de código y comentarios entre desarrolladores. Con esta tarea, la base de código del sitio queda oficialmente asociada a un repositorio Git privado.

- ### **Tarea 3: Crear la canalización de CI/CD con CodePipeline**
Una vez que el repositorio existía, el siguiente paso fue automatizar los despliegues para no depender de comandos manuales hacia S3. Para eso usé AWS CodePipeline. En lugar de crear la canalización desde la consola, en este laboratorio se utilizó un archivo JSON de configuración llamado cafe_website_front_end_pipeline.json, ubicado en la carpeta resources dentro del IDE de VS Code.
Primero abrí ese archivo y revisé su estructura. La definición de pipeline indicaba qué rol de IAM usaría (RoleForCodepipeline), qué bucket de S3 funcionaría como artifact store de la canalización y qué etapas tendríamos. La etapa de “Source” estaba configurada para tomar el código del repositorio front_end_website en la rama main, y la etapa de “Deploy” estaba diseñada para desplegar en un bucket de S3 que hospeda el sitio de la cafetería. En esa configuración de despliegue se especificaba el nombre del bucket destino, la extracción automática de los contenidos del zip y un valor de CacheControl con max-age=14, que más adelante se verifica en los encabezados HTTP.
Antes de crear la canalización, reemplacé los marcadores <FMI_1> por el ID de mi cuenta de AWS (obtenido con aws sts get-caller-identity) y el marcador <FMI_2> por el nombre real del bucket que tiene “s3bucket” en el nombre (obtenido con aws s3 ls). Después de guardar el archivo, ejecuté el comando aws codepipeline create-pipeline --cli-input-json file://cafe_website_front_end_pipeline.json, lo que creó la canalización en AWS.
En la consola de CodePipeline pude ver la pipeline llamada cafe_website_front_end_pipeline y revisar su estado. La canalización ya tenía conectada la fuente (CodeCommit) y el destino (S3). Como parte del flujo inicial, CodePipeline tomó el contenido del repo (que en ese momento solo era test.html) y lo desplegó automáticamente en el bucket del sitio. Para comprobar que esto funcionaba, obtuve el dominio de CloudFront con aws cloudfront list-distributions y abrí en el navegador la URL https://<cloudfront_domain>/test.html, donde vi la página HTML de prueba. Con eso confirmé que la canalización estaba activa y que cualquier cambio en el repo se puede reflejar en el sitio.

- ### **Tarea 4: Clonar el repositorio en el IDE de VS Code**
Aunque es posible editar archivos directamente en la consola de CodeCommit, resulta incómodo para desarrollos reales. Por eso, en la siguiente tarea cloné el repositorio en el entorno local del IDE de VS Code. En la consola de CodeCommit copié la URL para clonar (Clone HTTPS (GRC)), que es la que CodeCommit genera para este entorno de laboratorio.
En el terminal del IDE navegué un nivel arriba y ejecuté git clone <<Clone URL>>, lo que creó una carpeta local llamada front_end_website en ~/environment. Al terminar el clon, el archivo test.html se hizo visible en el explorador de VS Code. En este punto ya podía trabajar con el repositorio como en cualquier flujo de Git: editar archivos localmente, ver diffs, hacer commits y luego hacer push hacia CodeCommit, dejando que CodePipeline se encargue de desplegar el resultado.

- ### **Tarea 5: Usar la integración de Git en VS Code y gatillar la canalización**
Para practicar el flujo de cambios, primero exploré la pestaña de control de código fuente en VS Code (el ícono de la ramificación en la barra lateral). El IDE detectó automáticamente que la carpeta front_end_website era un repositorio Git y mostró la rama actual (main). Abrí el archivo test.html y modifiqué el título de la página para que dijera “Best test page ever.”. Al guardar, el indicador de cambios pendientes en el icono de Git mostró que había un cambio sin confirmar.
Desde la vista de Source Control, ingresé como mensaje de commit “Updated the title” y utilicé la opción “Commit & Push” para confirmar y subir el cambio directamente desde el IDE a CodeCommit. Esto automáticamente disparó una nueva ejecución de CodePipeline. Volví a la consola de CodeCommit para revisar los commits, y en la vista de diferencias pude ver claramente la línea anterior con el título viejo (resaltada en rojo con un signo menos) y la nueva línea en verde con el signo más.

> A continuación regresé a la URL https://<cloudfront_domain>/test.html y recargué la página. Después de algunos segundos, el título de la pestaña del navegador ya mostraba el nuevo texto “Best test page ever.”. Eso valida que el ciclo completo funciona: edito en VS Code, confirmo cambios, hago push a CodeCommit y CodePipeline despliega automáticamente la nueva versión al bucket S3 que alimenta CloudFront.

- ### **Tarea 6: Migrar el código real del sitio y validar la configuración de caché**
Hasta ese momento el repositorio solo contenía una página de prueba, pero el objetivo real era que el repositorio de CodeCommit se convirtiera en la fuente oficial del código del sitio de la cafetería. Para lograr esto, eliminé el archivo test.html de la carpeta front_end_website en el IDE de VS Code y luego copié el contenido real del sitio desde ./resources/website hacia front_end_website, usando los comandos:
> cd ~/environment
> cp -r ./resources/website/* front_end_website
> rm -r ./resources/website

De esta forma el sitio completo (HTML, CSS, JavaScript y demás assets) pasó a estar dentro del repositorio Git. Luego volví a la vista de control de código fuente en VS Code, donde aparecían todos los nuevos archivos listos para ser confirmados. Ingresé un mensaje de commit tipo “Providing the website” y utilicé nuevamente la opción “Commit & Push” para subir todo el código al repo central.
CodePipeline se activó de nuevo y tomó el contenido del repo como fuente. Volví a la URL de CloudFront pero esta vez eliminé /test.html y dejé solo https://<cloudfront_domain>/. Al refrescar la página, el navegador ya mostraba el sitio completo de la cafetería, lo que indicaba que el código del sitio real ya se estaba sirviendo desde el bucket actualizado por la canalización.
Como paso final, verifiqué que la configuración de cache-control definida en el archivo JSON de la canalización se estuviera aplicando correctamente. Abrí las herramientas de desarrollador del navegador, cargué el sitio y en la pestaña Network seleccioné uno de los archivos JavaScript, por ejemplo pastries.js. En los encabezados de respuesta revisé el valor de cache-control y confirmé que estaba configurado en max-age=14. Esto significa que la canalización no solo sube los archivos, sino que además controla la política de caché del contenido estático, asegurando que el navegador use la versión más reciente sin dejar de aprovechar la caché.

- ### **Conclusión general**
Con este laboratorio logré cerrar el ciclo de automatización alrededor del sitio web de la cafetería. Ahora el código del frontend está centralizado en un repositorio privado de AWS CodeCommit, lo que permite un control de versiones claro, auditoría de cambios y colaboración entre varios desarrolladores. Al mismo tiempo, CodePipeline queda configurado como una canalización CI/CD que toma la rama principal del repositorio, empaqueta los cambios y los despliega automáticamente sobre el bucket de S3 que sirve el sitio estático a través de CloudFront.
Desde la perspectiva de Sofía, esto significa que ya no tiene que estar recordando comandos ni subir archivos manualmente a S3 cada vez que hace una pequeña modificación. Solo necesita trabajar en el IDE, hacer commit y push, y dejar que la canalización haga el resto. Para Frank, esto se traduce en un sitio más mantenible, que puede crecer con nuevas características sin perder trazabilidad de qué cambió, cuándo y quién lo hizo. Y en términos de buenas prácticas, se introduce formalmente el uso de CI/CD en el proyecto, sentando las bases para futuras extensiones como pruebas automatizadas, entornos por etapas y flujos de aprobación de código antes del despliegue a producción.
